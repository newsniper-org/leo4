# SPEC: OX8 — rust-transpile path reverse direction

Status: **DRAFT** (opened 2026-05-27, follows OX7 γ-1').
Scope: **v1.0 RC blocker** (promoted from v1.x, 2026-05-27 — per
user instruction OX7 and OX8 both ship before v1.0 RC).
Owner: leo4 (윤병익) + Team Kitasan (cool-japan/oxilean upstream
for the OxiLean-side pieces).

## 1. Motivation

leo4 ships two directions:

- **Forward**: Lean code calls Rust. The user writes Lean, decorates
  exports with `@[leo4_export]`, and leo4 generates a Rust crate that
  invokes the Lean side. Today: implemented for both `mslean4` (lake +
  shim) and `rust-transpile` (zero-lake, native Rust via OxiLean
  transpile).
- **Reverse**: Rust code exposes `#[leo4::export]` functions, Lean
  calls them. Today: implemented for `mslean4` only — lake plugin
  emits `<iface>/Rust.lean` wrappers and Lake's `extern_lib`s pull in
  the dispatcher / glue archives.

The `rust-transpile` impl is the lake-free path. **It has no reverse
support yet**. OX8 closes that gap.

### 1.1 Concrete driver — adsmt OxiLean bindings

`~/AD1/` (`Honey-Be/adsmt`) is the flagship reverse-direction demo
consumer. Today adsmt's Lean integration is hand-written:

- `adsmt-ffi` crate exposes a `cdylib` with C ABI symbols
  (`adsmt_solver_new`, `adsmt_solver_check_sat`, …).
- `lean/Adsmt/Ffi.lean` declares matching `extern` Lean bindings
  manually.
- `lakefile.toml` glues the cdylib into a Lake project.

The "Phase 10 reverse-direction demo" plan was to replace the
hand-written FFI surface with leo4-generated bindings. That works
today only via `--impl mslean4` (lake-driven).

adsmt's *OxiLean bindings* — the variant that doesn't need a Lean
toolchain installed and runs inside an OxiLean-elab-driven
environment — needs the rust-transpile path to ship reverse support.
OX8 is the prerequisite.

## 2. Architecture chosen — option (A) OxiLean-driven Lean side

Reverse layout under `--impl rust-transpile`:

```
adsmt-like-project/
├── Cargo.toml            # cdylib + leo4 deps (same as mslean4 reverse)
├── src/lib.rs            # #[leo4::export] functions
├── leo4.toml             # kind = "rust-transpile"
├── lean/
│   ├── Main.lean         # user's Lean entry point — calls into the wrappers
│   └── <Iface>/Rust.lean # generated wrappers (`extern` decls bound to cdylib)
└── transpiled/           # generated by `leo4 run` — empty for pure-reverse,
                          # or holds Lean-side helper transpile output if the
                          # user also writes forward-style helpers.
```

Runtime model:

1. **Build**: `cargo build --release` produces the cdylib exactly the
   way mslean4 reverse does. `#[leo4::export]` macro output is
   identical — the cdylib's C ABI is impl-independent.
2. **Wrapper emit**: `leo4-oxilean-build` (extended for reverse — new
   subcommand or `--mode reverse` flag) reads the cdylib's
   `EXPORTS` slice (the leo4 cross-impl-conformant export table) and
   emits `lean/<Iface>/Rust.lean` containing matching `@[extern …]`
   declarations. This step replaces `lake run
   Leo4Rust/regenerate`.
3. **Lean-side elab + dispatch**: `sibling/leo4-oxilean` (the OxiLean
   adapter; currently scaffold-only) loads the generated `.lean`
   file via OxiLean's `oxilean-elab`, sees the `@[extern]`
   declarations, and at evaluation time dispatches to the cdylib
   via `libloading` — the same trick leo4-rust-bridge uses on the
   forward path.
4. **`leo4 run --impl rust-transpile`** (reverse direction) drives
   the full pipeline: cargo build → wrapper emit → leo4-oxilean
   evaluator on the user's `lean/Main.lean`.

The Lean source is never compiled by `leanc`. lake is never invoked.
The Lean toolchain isn't installed on the user's machine. The only
runtime dependency is OxiLean's evaluator (already shipped in
oxilean-runtime, used by leo4-oxilean).

## 3. Out of scope

- mslean4 path changes — OX8 touches only `rust-transpile`.
- Multi-impl projects mixing forward + reverse in one crate —
  doable, but defer until the single-direction path is solid.
- adsmt's actual migration to leo4 bindings — that lives in `~/AD1/`,
  not in leo4. OX8 just makes the migration *possible*.

## 4. Phases

Each phase is one commit (give or take), with explicit acceptance
criteria. Numbering deliberately avoids overlap with OX7 codegen
fixes — those proceed in parallel.

### Phase OX8.1 — leo4-oxilean adapter audit

Inventory the current state of `sibling/leo4-oxilean/`. The runtime-
dispatch adapter is mentioned throughout the codebase but is
scaffold-only. Document: what's wired, what's missing for reverse,
and whether OX7 codegen fixes (`Const` name preservation, native
type mapping, declared `ret_type`) are sufficient for the evaluator
to dispatch correctly.

**Acceptance**: a written audit (in `LEO4-DESIGN.md` §9 or a new
file under `docs/`) listing concrete gaps.

### Phase OX8.2 — Reverse wrapper emit in leo4-oxilean-build

Add a `leo4-oxilean-build --mode reverse` (or `--reverse-from-cdylib
<path>`) subcommand that:

- Loads the cdylib produced by `cargo build --release -p <user-pkg>`.
- Reads the leo4 `EXPORTS` slice using the same shape leo4-rust-emit
  consumes today.
- Writes `lean/<Iface>/Rust.lean` containing one `@[extern
  "<mangled>"] def <pretty>(…) : …` per export.

Output is parser-compatible with the mslean4 path's wrapper output
(verified by diff-test against a small fixture). The generated
`.lean` file is in oxilean-parse-peg's accepted surface; if not, OX6
parser gets extended in a separate commit.

**Acceptance**: round-trip test under `tests/conformance/`:
given a Rust fixture with two `#[leo4::export]` fns, the wrapper
emitted by leo4-oxilean-build round-trips through oxilean-parse-peg
without errors.

### Phase OX8.3 — leo4-oxilean evaluator's `@[extern]` dispatcher

Extend `sibling/leo4-oxilean` so the OxiLean evaluator handles
`@[extern "mangled_name"]` by `libloading` the named symbol from the
configured cdylib path. Uses the same canonical-ABI marshalling
already implemented for the forward path's `leo4_call` (zero new
ABI design).

**Acceptance**: a Lean source like `def x : UInt64 := Sample.add 1
2` (where `Sample.add` is an `@[extern]` decl pointing at a cdylib)
evaluates to `3` end-to-end in `leo4-oxilean`.

### Phase OX8.4 — `leo4 run --impl rust-transpile` reverse branch

Detect `direction = Reverse` in the leo4-cli wire-up (the same
`detect_direction` already running for mslean4 reverse) and dispatch
to a new `run_reverse_rust_transpile` runner that:

1. `cargo build --release -p <pkg>` (existing leo4-cli helper).
2. `leo4-oxilean-build --mode reverse --cdylib <path> --out
   lean/<Iface>/Rust.lean` (phase OX8.2 output).
3. `leo4-oxilean eval lean/Main.lean` (phase OX8.3 output).

Emits the same OX7 experimental warning until (1b) lands and adsmt
fixture passes end-to-end.

**Acceptance**: `leo4 run --impl rust-transpile` works on a stripped-
down adsmt-shape scaffold in `examples/`. T7 doc gets a sibling
section.

### Phase OX8.5 — Scaffold update

`leo4 create reverse --impl rust-transpile` produces the OX8 layout
(replaces today's reject in `check_impl_supported`).

**Acceptance**: `leo4 create reverse … && cd … && leo4 run` works on
the scaffold's default fixture.

## 5. Dependencies on other tracks

- **OX7 (1a, #1, #2)** — landed. Const name + ret_type + native
  scalars all needed for the wrappers to be useful.
- **OX7 (1b)** — desirable but not strictly blocking. The reverse
  path doesn't transpile Lean → Rust for the wrapper module (it
  emits raw `@[extern]` decls), so (1b)'s elab bloat issue doesn't
  surface in the same way. The user's *body* Lean code (e.g.
  `lean/Main.lean`) does go through elab + LCNF if it has its own
  definitions; (1b) matters there.
- **OX6 parser** — already covers `@[extern]` decl syntax per the
  existing parse_decls tests. Re-verify with the exact wrapper
  emit shape from OX8.2.

## 6. Open questions

- **leo4-oxilean's status** — phase OX8.1's audit answers this. May
  reveal additional sub-phases.
- **adsmt as in-tree example vs. external** — `examples/` should
  probably get a tiny synthetic reverse fixture for OX8.4, since
  adsmt itself lives outside leo4 (per the existing
  `reference_adsmt` memory). The actual adsmt migration commit
  lives in `Honey-Be/adsmt`, not here.
- **Cross-impl conformance fixture** — does mslean4 reverse and
  rust-transpile reverse produce wire-identical cdylib calls? Almost
  certainly yes (the cdylib is identical, the dispatcher is
  different), but add a conformance test under
  `tests/conformance/` to assert it.

dependency-wise. OX8.1 (audit) is the gate — once that's written,
OX8.2 → OX8.5 are commit-sized each. Rough estimate: 4–7 days of
focused work + however long the OX7 (1b) parallel track takes.
